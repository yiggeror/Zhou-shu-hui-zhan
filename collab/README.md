# 协作区：Claude ⇄ Limo（Codex 里的 Astra）

这是 Claude（Claude Code）和 Limo（Codex 里的 Astra）合作做《咒术回战》新宿决战动画短片的交流区。
用户（项目主人）负责拍板；我们两个通过这个文件夹沟通、交付文件。

## 位置和规则

**每条消息、每份交付说明，开头第一行先表明身份**，格式：

```
【Claude → Limo】2026-10-03　需求 001：……
【Limo → Claude】2026-10-04　回复 001：……
```

这样任何人打开文件都知道是谁写给谁的，不会搞混。

**不修改对方写的文件**（包括不"顺手改一下"）。想更正、补充或反对对方的内容，就新写一条消息，引用对方的文件名说明。
自己写过的文件要改，也最好新开一条消息说明改了什么，而不是悄悄覆盖。

- 仓库：`yiggeror/Zhou-shu-hui-zhan`，分支：`claude/loving-keller-1bvt18`，文件夹：`collab/`。
- **各写各的文件夹，不改对方的文件**，这样同时提交也不会冲突：
  - `collab/to_limo/`：只有 Claude 写。需求和消息，编号 `001_xxx.md`、`002_xxx.md`……
  - `collab/from_limo/`：只有 Limo 写。每个需求一个子文件夹，例如 `from_limo/001/`，里面放图片和一个 `README.md`（开头表明身份，然后是交付清单、说明、遇到的问题）。不属于某个需求的消息，用 `from_limo/msg_001_xxx.md` 这样编号。
  - `collab/README.md`（本文件）和底部的进度表由 Claude 维护；Limo 想改规则或进度，请写消息告诉 Claude。
- 推送前先 `git pull --rebase origin claude/loving-keller-1bvt18`。
- 提交信息开头标明是谁：`[Limo] 001 角色设定图` / `[Claude] 需求 002`。
- 单个文件小于 100 MB（GitHub 限制）。图片用 PNG。
- 有问题、做不到、或者有更好的办法，直接写在回复里，不用勉强照做。

## 项目目标（用户定的）

做一部**像样的、真正有质量的**新宿决战动画短片，参照 NinjaristicNinja 的 MMV（《[MMV] Gojo vs Sukuna | Jujutsu Kaisen x coldrain》）的镜头和节奏。
用户明确最看重五件事：**人物面容形象、镜头叙事、打斗动作、咒术特效、整体画面精细度**。不必拘泥最初的"火柴人"提示词。

## 之前失败过的路（不要重走）

1. **AI 重绘关键帧 + 变形 / 插值**（四个版本 + A 版，518 张重绘图）：被评价"像木偶""完全是静止画面"。原因：只有少量关键帧时，变形和插值做不出新姿势，手脚头发衣服都不会真正动。
2. **代码画火柴人**（照搬 126 个镜头）：人物没有脸、没有形象，特写和反应镜头完全读不懂。
3. **照描原片位置的火柴人**：动作扭曲变形，不明所以。

## 路线：逐张作画（2026-10-03 定）

用户要**像动漫一样的画面**（二维手绘质感），而且动作要真的在动。Limo 能大量生成图片（不能生成视频），所以：

- **Limo 逐张作画**：像真正的动画一样，每个镜头一张一张地画。打斗一秒约 8–12 张（一拍二、一拍三），安静的镜头少画、多停。人物、特效、背景分开画。
- **Claude 当导演、摄影和后期**：镜头设计、每张画什么、每张在第几帧出现（摄影表）、姿势和构图参考、特效、合成、镜头运动、剪辑、逐帧检查，以及给 Limo 的重画单。
- **角色设定图**保证全片人物长得一样，在测试通过后做。
- 不再用三维建模（容易有"三维游戏感"），也不再用"少量关键帧 + 变形 / 插值"（之前失败过）。
